# BobCourse-AI — Master Project Plan

## Top-Level Overview

**Project:** BobCourse-AI — University Course Evaluation System
**Role:** Software Engineer (individual, bootcamp submission)
**Goal:** Build a complete, professional, full-stack electronic course evaluation system that allows students to rate and comment on courses, instructors to view anonymized aggregated results, and administrators to manage the academic structure and analytics — all within a 7-day sprint.
**Stack:** React + TypeScript + Vite + React Query (Frontend) → Python FastAPI (Core Service) → Java Spring Boot (Analytics Service) → PostgreSQL

The plan is organized as a sequence of independently completable sub-tasks, each with clear intent, expected outcomes, and ordered steps. No code is written until the user approves this plan.

### C.2 Architecture Decision: Java Has No Direct DB Access

Java receives raw submission data in the REST request payload from Python and returns computed analytics. This keeps PostgreSQL ownership clean and avoids the complexity of a shared database or a separate Java-managed database in the MVP. This is a deliberate, human-judged architectural decision (see Section K).

### D.3 Anonymity Architecture

`evaluation_submissions` stores `student_id` for two purposes only:
1. Enforcing the one-submission-per-student constraint at insert time.
2. Admin auditing in case of abuse investigation (access-controlled).

The `student_id` is **never returned** by any instructor-facing API endpoint. The analytics Java service never receives `student_id`. Python strips it before any response. The `text_comments` table has no student reference — it links only to `submission_id`, which is itself opaque to instructors.

### E.2 Key Endpoint Definitions

#### Auth
- `POST /api/v1/auth/login` → `{ access_token, token_type }`
- `POST /api/v1/auth/refresh` → `{ access_token }`

#### Student Evaluation Flow
- `GET /api/v1/me/enrollments` → list of course offerings + campaign status
- `GET /api/v1/evaluation-campaigns/{id}/questions` → questions for submission
- `POST /api/v1/submissions` → submit answers + optional comment
  - Body: `{ campaign_id, answers: [{question_id, rating}], comment?: string }`
  - 409 Conflict if already submitted
  - 403 Forbidden if not enrolled or campaign not open

#### Analytics (proxied to Java)
- `GET /api/v1/analytics/campaigns/{id}` → campaign statistics
- `GET /api/v1/analytics/courses/{id}/trends` → trend over semesters
- `GET /api/v1/analytics/dashboard` → university-wide dashboard (admin only)
- `GET /api/v1/analytics/campaigns/{id}/export` → CSV download

#### AI Insights
- `POST /api/v1/ai-insights/campaigns/{id}/analyze` → trigger analysis (admin)
- `GET /api/v1/ai-insights/campaigns/{id}` → retrieve insights (admin + instructor threshold)
- `PATCH /api/v1/ai-insights/campaigns/{id}/review` → mark as human-reviewed (admin)

### E.3 Java Spring Boot Endpoints (Internal, Called by Python Only)

| Method | Path | Purpose |
|--------|------|---------|

## F. Security Model

### F.1 Authentication

- All passwords hashed with **bcrypt** (cost factor 12)
- JWT access tokens: short-lived (60 minutes), signed with HS256
- JWT refresh tokens: longer-lived (7 days), stored as HTTP-only cookie
- Token payload: `{ sub: user_id, role: enum, exp, iat }`
- All secrets via environment variables (never hardcoded)

### F.2 Authorization (RBAC)

| Resource | Student | Instructor | Admin |
|----------|---------|------------|-------|
| Own profile | R/W | R/W | R/W |
| Academic structure | R | R | CRUD |
| Other users | — | — | CRUD |
| Enrollments | Read own | — | CRUD |
| Templates / questions | R | R | CRUD |
| Campaign open/close | — | — | W |
| Submit evaluation | W (own enrolled) | — | — |
| View own campaign results | ✓ (after threshold) | ✓ (own courses, threshold) | ✓ |
| Analytics dashboard | — | Own courses only | ✓ |
| AI insights | — | Own courses only | ✓ (trigger + review) |
| Audit logs | — | — | R |

### F.3 Anonymity Enforcement

- Python enforces: instructor-facing endpoints strip `student_id` from all response objects
- Minimum response threshold: if `submission_count < min_responses_threshold`, instructor endpoints return 403 with message "Insufficient responses for disclosure"
- Java never receives `student_id` — enforced at the Python service layer before every outbound call
- Admin can see aggregate counts but not individual student-to-submission mapping through normal API responses

### F.4 Input Validation

- All inputs validated via Pydantic 2 schemas (Python)
- All inputs validated via Spring Validation / Bean Validation (Java)
- Rating values constrained to 1–5 via CHECK constraint in DB and Pydantic validator
- Comment length max 2000 characters enforced in schema and DB
- SQL injection prevention via SQLAlchemy ORM parameterized queries

### F.5 Additional Security Measures

- CORS configured to allow only the frontend origin
- Environment variables for all secrets (`.env.example` provided, `.env` gitignored)
- Audit log entries written for: user creation, campaign open/close, AI analysis trigger, admin login, bulk data export

## G. Responsible AI Plan

### G.1 Principles

- AI output is advisory only — it must never be the sole basis for personnel decisions
- Every AI insight response includes a required `disclaimer` field
- All insights require human review before being considered official
- `human_reviewed` flag on `ai_insights` table must be set by an admin before the insight is "approved"

### G.2 PII Protection

- Before sending comments to any AI provider, a PII masking step is applied
- Masking replaces: email addresses, phone numbers, national ID patterns, and names that appear in a user-names lookup with `[REDACTED]`
- Masking is implemented as a pure Python function (deterministic, testable)
- Masked text is what gets analyzed — original text remains in the DB but is only accessible by admin

### G.3 AI Provider Architecture

```
AIProviderInterface (abstract base class)
    ├── OfflineFallbackProvider   ← default for MVP demo
    └── OpenAIProvider            ← real provider (requires API key)
```

- The active provider is selected via environment variable `AI_PROVIDER=offline` or `AI_PROVIDER=openai`
- `OfflineFallbackProvider` uses deterministic keyword-based heuristics to produce a demo-quality summary, sentiment, and themes — no external API call required
- Swapping providers requires only an env var change — no code changes

### G.4 AI Analysis Output Structure

```json
{
  "summary": "string",
  "sentiment": "positive | neutral | negative | mixed",
  "themes": ["string"],
  "improvement_areas": ["string"],
  "provider_used": "string",
  "disclaimer": "AI-generated insights are for reference only and must not be used as the sole basis for evaluating an instructor's performance.",
  "human_reviewed": false
}
```

### G.5 Responsible AI Documentation

A standalone `docs/responsible-ai.md` document will explain:
- What AI is used for
- What it is explicitly NOT used for
- The PII masking approach
- The human review requirement
- The offline fallback rationale
- Known limitations of the offline heuristic model

## H. Testing Strategy

### H.1 Python (pytest)

- **Unit tests:** Services layer — business logic, anonymity enforcement, threshold checks, PII masking, AI provider factory
- **Integration tests:** API endpoints using `TestClient` with a test database (SQLite in-memory or test PostgreSQL schema)
- **Coverage target:** 70% minimum for services and API routes
- Key test cases:
  - Student cannot submit duplicate evaluation
  - Student cannot submit for non-enrolled course
  - Instructor cannot see results below threshold
  - `student_id` is absent from instructor-facing responses
  - PII masking correctly redacts known patterns
  - Campaign status transitions (draft → open → closed)

### H.2 Java (JUnit 5)

- **Unit tests:** Each analytics service method tested with known inputs and expected outputs
- **Coverage target:** 80% minimum for service layer
- Key test cases:
  - Average calculation correct with known ratings
  - Distribution sums to 100%
  - KPI calculation edge cases (zero submissions, all 1s, all 5s)
  - Trend returns correct ordering across semesters
  - CSV output contains correct headers and row count

### H.3 Integration Test: Python → Java

- One dedicated integration test that starts both services and verifies:
  - Python correctly calls Java analytics endpoint
  - Java returns expected shape
  - Python correctly transforms and returns result to caller
- Can be run via `docker-compose` in CI

### H.4 Frontend Testing

- Not required for MVP — manual smoke testing is sufficient for bootcamp
- If time permits: one Vitest smoke test confirming the login page renders

### H.5 CI/CD (GitHub Actions)

- A GitHub Actions workflow (`.github/workflows/ci.yml`) runs on every push and pull request
- Jobs:
  1. **python-tests** — install dependencies, run pytest, fail on test failure
  2. **java-tests** — Maven build + test (`mvn test`), fail on test failure
  3. **lint-frontend** — `npm run lint` (ESLint)
- Jobs run in parallel where independent
- No deployment step in MVP — CI only (not CD)
- The workflow file and its run history are SDLC evidence

## K. Human Engineering Judgment Decisions

These are decisions where AI assistance was intentionally NOT followed blindly, or where the engineer applied professional judgment. Each must be documented in `docs/human-judgment.md`.

| # | Decision | Judgment Applied |
|---|----------|-----------------|
| 1 | Java has no direct DB access | Choosing simplicity over microservice purity for a 7-day MVP; shared-DB complexity would create more risk than benefit |
| 2 | One campaign per course offering | AI might suggest flexible multi-template-per-offering; engineering judgment chose simplicity and clear business semantics |
| 3 | Anonymity threshold of 5 (default) | Numeric threshold is an ethical and institutional policy decision, not a technical one — must be human-set |
| 4 | bcrypt cost factor 12 | Security/performance trade-off requiring human calibration; AI default suggestions vary widely |
| 5 | Offline AI fallback is the demo default | Responsible choice not to depend on paid external APIs for a bootcamp demo; also demonstrates offline capability |
| 6 | student_id never sent to Java | Anonymity is a human responsibility; this architectural constraint must be enforced by a human engineer, not delegated to AI |
| 7 | Exclusion of Kafka, Kubernetes, and API gateway | AI tools often suggest over-engineered infrastructure; human judgment applied to select the minimal viable architecture |
| 8 | No self-service password reset | Decision to exclude email/SMTP entirely rather than implement an insecure mock reduces the security surface area |
| 9 | Minimum threshold check on instructor access | The specific disclosure rule — when it's safe to reveal aggregated results — is an ethical/institutional policy decision |
| 10 | AI disclaimer text | The exact wording of the AI disclaimer is a responsible AI communication decision that must be reviewed by a human |

## L. Risks and Mitigations

| # | Risk | Impact | Mitigation |
|---|------|--------|-----------|
| 1 | Python–Java integration is the most complex part; getting the contract wrong will cascade | High | Define the full DTO contract in Phase 6 before Python calls it; write contract test early |

| 4 | AI analysis fails in demo without an API key | Medium | Offline fallback is mandatory and is the default; demo requires zero external keys |

## M. Explicit Out-of-Scope List

The following are explicitly excluded from the 7-day MVP:

1. **Email / SMTP integration** — no password reset emails, no notification emails
2. **OAuth2 / SSO / social login** — only username + password
3. **Real-time features** — no WebSockets, no push notifications
4. **File uploads** — no profile pictures, no PDF submissions
5. **Rich text / Markdown** in comments — plain text only
6. **Mobile-native app** — responsive web only
7. **Multi-language / i18n** — English only
8. **Kafka / RabbitMQ / message queues** — synchronous HTTP only
9. **Kubernetes / Helm / service mesh** — Docker Compose only
10. **API Gateway** (Kong, Nginx as gateway) — direct service calls
11. **CI/CD pipeline** — manual docker-compose run; git history is SDLC evidence
12. **Complex reporting scheduler** — CSV export on demand only
13. **Student grade data** — evaluations are independent of grades
14. **Admin viewing individual student submissions** — only aggregates and anonymized comments
15. **Student ability to edit or withdraw submitted evaluations** — submissions are final

## N. Final Recommendation

**This design is realistic for a 7-day individual project with the following conditions:**

### Why It Is Realistic
- The MVP scope is tightly bounded — 15 entities, clearly defined endpoints, no over-engineering
- Java is scoped to pure computation with no DB access — reducing integration complexity to a single REST contract
- The offline AI fallback eliminates any external API dependency
- Docker Compose handles infrastructure, not Kubernetes
- FastAPI auto-generates API documentation, eliminating a manual docs step
- All 12 bootcamp requirements are traceable to concrete artifacts

### Critical Path (Must Complete in Order)
1. Phase 0 → Phase 1 → Phase 2 (unblock all further backend work)
2. Phase 6 (Java) can run in parallel with Phases 3–5
3. Phase 7 (integration) only after both Phase 5 and Phase 6 are done
4. Phase 9 (Frontend) can start in parallel after Phase 2 (auth endpoints exist)
5. Phase 10 (docs) is continuous but final assembly is last

### Biggest Risk to Completion
The Python → Java integration contract. If the DTO shape is not agreed upon before both sides start coding, rework will occur. The plan resolves this by defining the full contract in this document (Section E.3) before any code is written.

### Honest Assessment
A disciplined engineer following this plan can complete a fully working, professional-grade submission. The documentation requirements are substantial but are built into the plan as Phase 10 with specific file-by-file tasks.
